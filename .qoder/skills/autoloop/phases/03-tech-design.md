# P3 技术方案（tech-design）

## 目标
把 PRD 转化为可直接照做的技术方案：架构落点、具体到路径的文件清单、到字段级的跨模块契约、兼容与回滚方案、测试策略。P4 实现阶段照本方案执行，因此本阶段的质量直接决定实现阶段是否会返工——方案里省略的细节，实现时就会变成随意的决定。

## 输入
- `artifacts/P1-requirement-card.md` 与 `artifacts/P2-prd.md`（全量读取）。
- 相关 lessons 条目（若有）。
- 代码库现状：必须实际读代码确认现有架构与约定（EZLove 三端架构、API 路由前缀映射、数据库迁移机制见仓库 AGENTS.md）。

## 执行者
Research 型子代理（技术方案设计，本阶段不改代码，但必须实际浏览代码库核实落点）。派遣提示必须包含：P1、P2 产物全文、本模板"执行指令"全文、仓库架构要点（三端目录、四层后端结构 model→schema→service→api、Alembic 迁移约定）、相关 lessons 条目。

## 执行指令
1. 架构描述：改动落在哪些模块/端，为什么这样落（对照仓库现有分层与路由前缀映射；新增路由须注册到 `backend/app/api/v1/router.py`，新增模型须在 `models/__init__.py` 导入——遵循仓库既有规则）。
2. 涉及文件清单必须**具体到路径**，按"新增 / 修改 / 删除"三组列出，每个文件一行说明改什么。禁止只写模块名或目录名。
3. 跨模块契约（API/Schema/事件/DB 迁移）必须**写明字段**：字段名、类型、必填性、语义、示例值。新增表要给出完整字段表与索引；修改已有表必须走 Alembic 迁移并写迁移要点。
4. 兼容与回滚：改动对现有调用方/数据的影响分析；回滚方案必须可执行（写清触发条件、回滚步骤、数据如何处理），"可回滚"三个字不算方案。
5. 测试策略：与 P1 验收标准逐条对应，写明每条标准用单测/集成/手动冒烟哪种方式覆盖、落在哪些测试位置。
6. 明确技术选型与理由（引入新依赖须说明必要性）。
7. 产物自包含，实现者只读此文件 + PRD 即可开工。

## 必须产出物
- `artifacts/P3-tech-design.md`（技术方案），固定章节：

| 章节 | 内容要求 |
|---|---|
| 架构 | 模块落点与理由，含与现有架构的关系 |
| 涉及文件清单 | 新增/修改/删除，具体到路径 |
| 数据契约 | API/Schema/DB 字段级定义 |
| 兼容与回滚 | 影响分析 + 可执行回滚方案 |
| 测试策略 | 与验收标准逐条映射 |

## 质量对照示例

- 差的文件清单："后端相关文件若干"。→ 实现者无从下手，P6 无法逐项核销。
- 好的文件清单："新增 backend/app/models/canteen_menu.py（菜单表 ORM，字段见契约 §3）；修改 backend/app/api/v1/router.py（注册 /community/canteen/menus 路由）"。→ 到路径、到改动点。
- 差的契约："接口返回菜单信息"。→ 字段不明，前后端各自想象。
- 好的契约："GET /api/v1/community/canteen/menus/weekly → { days: [{ date: string(YYYY-MM-DD, 必填), items: [{ name: string(必填), price: number(必填, 单位分) }] }] }"。→ 字段、类型、必填、单位俱全。
- 差的回滚："出问题可回滚"。→ 不可执行。
- 好的回滚："触发条件：冒烟项 2/3 失败。步骤：① git revert <merge-commit>；② alembic downgrade -1；③ docker-compose up -d --build backend。数据处理：新增表数据保留不影响旧代码"。→ 命令级可照做。

## 迭代与改进约定

- 本阶段 gate 失败后，用 `python3 .qoder/skills/autoloop/scripts/harness.py directives --run <run-id>` 获取改进指令，据此修订方案，并在文件尾部追加「改进记录」一节（轮次 / 收到的指令 / 修订内容），供评审核验改进轨迹。
- 修订只针对指令指向的问题，不重写未受影响的章节；方案变更波及 P1/P2 产物时，同步在下游阶段引用处注明（不回头改已通过的阶段产物）。
- 方案级新歧义（评审发现的遗漏场景）按 P1 的默认决策风格处理：在方案中拍板并写理由。
- 超过迭代上限（默认 5 轮）进入 blocked：停止修订，向用户呈报记分卡与未决指令，等待决策。

## 完成标准
- [ ] 文件清单全部到路径级，三组（新增/修改/删除）划分清晰。
- [ ] 所有跨模块契约到字段级（名称/类型/必填/语义），含示例。
- [ ] 涉及 DB 变更的部分明确 Alembic 迁移要点与向后兼容处理。
- [ ] 回滚方案包含触发条件与具体步骤，可直接执行。
- [ ] 测试策略覆盖 P1 全部验收标准，无遗漏项。
- [ ] 文件清单与仓库实际结构吻合（路径真实存在或明确标注为新增）。
- [ ] 迭代轮次产生的改进记录完整可追溯（若经历过重评）。

## 评分要点（摘要）
- 最看重：文件清单的具体性（到路径）、数据契约的完备性（到字段）、回滚方案的可执行性。
- 常见扣分：只写模块名不写路径；契约缺字段类型或必填性；回滚只写一句"可回滚"；测试策略与验收标准对不上号；方案与仓库既有分层规则冲突。
- veto 触发：无回滚方案；涉及数据结构变更却无迁移说明；文件清单与代码库事实明显不符（路径不存在且未标注新增）。
