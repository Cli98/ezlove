# P7 发布（release）

## 目标
完成全部发布准备并形成规范发布报告：版本号与 changelog、真实构建证据、可照做的部署步骤、部署后冒烟清单、可执行回滚方案。**本阶段有一条安全红线（safety.auto_deploy=false）：一切实际部署动作（含 git push、远程发布、生产变更）必须先获得用户明确确认，本阶段只做"准备就绪"，不做"实际执行"。**

## 输入
- `artifacts/P6-review-report.md`（放行前置：blocker 必须已清零）及 P1-P5 全部产物。
- 代码分支 `autoloop/<run-id>`（应已包含 P5/P6 修复后的最终状态）。
- 部署事实：仓库现有部署方式（Docker Compose + 阿里云 ECS，见 DEPLOYMENT_GUIDE.md）。

## 执行者
Coding/运维型子代理。派遣提示必须包含：P6 整合判断、P4 变更清单、本模板"执行指令"全文、安全红线原文、仓库部署指南要点、相关 lessons 条目。

## 执行指令
1. 版本号遵循仓库现有版本规则（无既有规则则采用语义化版本并在报告中说明依据）；变更范围与版本幅度匹配（纯修复→patch，新功能→minor）。
2. changelog 按 conventional 风格编写：与 P4 变更清单逐条对照，**用户可读**的表述（不是 diff 罗列），归类 Added/Fixed/Changed/Removed。
3. 构建证据：真实执行生产构建（如 `npm run build:mp-weixin`、`npm run build`、后端镜像构建）并粘贴关键输出（成功标志、产物大小/数量、警告项）。
4. 部署步骤清单：编号步骤、每步含具体命令与预期输出，可让任何人照做；前置条件（备份、迁移、配置变更）单独列出。
5. 部署后冒烟清单：上线后必查项（健康检查 `curl http://localhost:8001/health`、核心流程抽样），每项写预期结果。
6. 回滚方案：触发条件（什么现象回滚）+ 具体步骤（命令级）+ 数据处理（迁移是否需要 downgrade、产生的新数据怎么办）。
7. **安全红线执行方式**：报告中"实际部署"一节只写"待用户确认后执行"，并列出需要用户确认的精确动作清单（如 `git push origin autoloop/<run-id>`、`docker-compose up -d --build backend`）。把确认请求呈报给用户，等待明确答复。

## 必须产出物
- `artifacts/P7-release-report.md`（发布报告），固定章节：

| 章节 | 内容要求 |
|---|---|
| 版本与 changelog | 版本号 + 依据，conventional 分类 |
| 构建证据 | 真实构建命令与输出 |
| 部署步骤 | 编号步骤 + 前置条件，命令级 |
| 冒烟结果 | 部署后检查项 + 预期（未部署则标"待部署后执行"） |
| 回滚方案 | 触发条件 + 步骤 + 数据处理 |
| 待用户确认的部署动作 | 精确命令清单，标注"未获确认未执行" |

## 用户确认流程

1. 报告完成后，向用户呈报"待用户确认的部署动作"清单（精确到命令）。
2. 用户明确同意 → 由编排 Agent 按部署步骤执行 → 把每步实际输出补记入报告新增「部署执行记录」一节 → 执行冒烟并回填冒烟结果。
3. 用户不同意或要求修改 → 记录用户意见，按意见调整部署方案后重新呈报。
4. 未获答复 → 保持"准备就绪"状态，不得推进，也不得自行视为 blocked（这是等待用户，不是流程卡死）。

## 迭代与改进约定

- 本阶段 gate 失败后，用 `python3 .qoder/skills/autoloop/scripts/harness.py directives --run <run-id>` 获取改进指令，据此修订发布报告（版本/changelog/步骤/回滚），并在文件尾部追加「改进记录」一节（轮次 / 收到的指令 / 修订内容）。
- 指令指向构建失败、changelog 与 diff 不符等问题时，必须重新真实构建/重新对照后修订，禁止只改文字。
- 迭代与用户确认是两个独立门：评分门通过不代表部署已授权，两道门都过才能实际发布。
- 超过迭代上限（默认 5 轮）进入 blocked：停止修订，向用户呈报记分卡与未决指令，等待决策。

## 完成标准
- [ ] 版本号有依据，changelog 与 P4 变更清单可对照、无遗漏无虚报。
- [ ] 构建证据为真实输出（与 P5 证据风格一致，可复现）。
- [ ] 部署步骤可照做（每步有命令与预期输出），前置条件齐全。
- [ ] 回滚方案含触发条件、命令级步骤、数据处理三要素。
- [ ] "待用户确认的部署动作"清单明确，且报告内无任何"已执行部署"的记录。
- [ ] 迭代轮次产生的改进记录完整可追溯（若经历过重评）。

## 评分要点（摘要）
- 最看重：回滚方案完备性、部署步骤可照做性、changelog 与变更的事实一致性。
- 常见扣分：部署步骤写"按常规流程部署"；回滚缺数据处理；changelog 漏项或夸大；冒烟清单只写"验证服务正常"；构建输出疑似旧跑结果。
- veto 触发：**未经用户确认执行了任何实际部署/推送动作**；无回滚方案；changelog 与 diff 事实不符；P6 blocker 未清零即进入发布准备。
