# P1 需求澄清（intake）

## 目标
把用户的一句话需求拆解为结构化需求卡：明确背景、目标、范围边界与可验证的验收标准，把所有歧义点转化为有理由的"默认决策"。本阶段是整条流水线的地基——后续所有阶段的产物都以此为准，需求卡上的含糊会在下游被放大为返工。

## 输入
- 需求原文（run 初始化时记录于 state.json，即 `python3 .qoder/skills/autoloop/scripts/harness.py init "<一句话需求>"` 传入的原文）。
- 历史经验（若存在）：`.autoloop/lessons/lessons.md` 中与本项目/需求类型相关的条目。
- 仓库现状：可浏览代码库了解现有能力（只读，不改代码）。

## 执行者
Research 型子代理（分析与写作，不做任何代码改动）。派遣提示必须包含：需求原文全文、本模板"执行指令"全文、相关 lessons 条目、仓库技术栈概览（EZLove：uni-app 小程序 / Vue3 管理后台 / FastAPI 后端）。

## 执行指令
1. 逐句拆解需求原文，列出所有歧义点（一个词有多种理解即为歧义，如"提醒"是推送还是红点、"上线"是生产还是预发）。
2. 每个歧义点必须给出**默认决策**：选择一种解释 + 一条理由 + 影响范围。禁止留空、禁止写"TBD/待定/待用户确认"。
3. 验收标准必须**可验证**：每条要能写出"执行什么命令 / 观察什么界面行为 / 检查什么数据"来判定通过与否。禁止"功能正常运行""体验良好"这类不可验证表述。
4. 明确划分范围与非目标：本次做什么、明确不做什么（非目标同样重要，防止范围蔓延）。
5. 识别风险：技术依赖、数据兼容、与现有功能的冲突，每条风险给出初步缓解思路。
6. 产物自包含：评审者只读这份文件即可理解需求全貌，不得引用对话历史。

## 必须产出物
- `artifacts/P1-requirement-card.md`（需求卡），固定章节：

| 章节 | 内容要求 |
|---|---|
| 背景 | 为什么要做，服务谁 |
| 目标 | 做成什么样（可描述的结果） |
| 范围 | 本次改动的边界，涉及的功能面 |
| 非目标 | 明确不做的事 |
| 验收标准 | 逐条可验证，编号列出 |
| 开放问题与默认决策 | 每个歧义：问题 / 默认决策 / 理由 |
| 风险 | 风险 / 影响 / 缓解思路 |

## 质量对照示例

- 差的验收标准："食堂菜单功能正常"。→ 不可验证，无法判定通过与否。
- 好的验收标准："管理后台新建每周菜单后，GET /api/v1/community/canteen/menus/weekly 返回本周 7 天菜单且每天 ≥1 条；小程序食堂页展示相同数据"。→ 可验证（有接口、有阈值、有对照面）。
- 差的默认决策："提醒方式待定"。→ 留白，下游无法开工。
- 好的默认决策："提醒方式默认采用小程序订阅消息而非短信：已有订阅消息基础设施，短信有成本与到达率风险；若用户后续明确要求短信再扩展"。→ 有选择、有理由、有边界。

## 迭代与改进约定

- 本阶段 gate 失败后，用 `python3 .qoder/skills/autoloop/scripts/harness.py directives --run <run-id>` 获取改进指令，据此修订需求卡，并在文件尾部追加「改进记录」一节（轮次 / 收到的指令 / 修订内容），供评审核验改进轨迹。
- 修订只针对指令指向的问题，不重写未受影响的章节（保留已认可的成果，降低回归风险）。
- 与用户的交互边界：默认决策优先自行拍板并记录理由；只有当歧义影响"做或不做"（方向级）而非"怎么做"（实现级）时，才向用户提问。
- 超过迭代上限（默认 5 轮）进入 blocked：停止修订，向用户呈报记分卡与未决指令，等待决策。

## 完成标准
- [ ] 七个章节齐全且非空。
- [ ] 每条验收标准可独立验证（能写出验证方法）。
- [ ] 所有识别到的歧义均有默认决策，无遗留开放问题（有决策但未拍板的必须升格为决策）。
- [ ] 范围与非目标边界清晰，不重叠。
- [ ] 风险至少覆盖技术、数据、兼容三个视角（若无风险须写明"经排查无 X 风险"及依据）。
- [ ] 迭代轮次产生的改进记录完整可追溯（若经历过重评）。

## 评分要点（摘要）
- 最看重：验收标准的可验证性、歧义处置（默认决策）的完备性。
- 常见扣分：验收标准空泛不可测；开放问题留白；范围与非目标混淆；背景与目标写成同一句话。
- veto 触发：缺"验收标准"或"开放问题与默认决策"章节；验收标准全部不可验证；把关键决策推给"待用户确认"而不给默认方案。
