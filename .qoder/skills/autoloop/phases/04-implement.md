# P4 研发实现（implement）

## 目标
严格照 P3 技术方案把功能实现出来，并产出如实的实现报告。本阶段的纪律是"忠实执行 + 诚实记录"：实现可以与方案有偏差（现实中常常必须偏差），但每个偏差必须在报告中声明原因；禁止超出方案范围顺手改动无关文件。

## 输入
- `artifacts/P3-tech-design.md` 与 `artifacts/P2-prd.md`（全量读取，方案是唯一实现依据）。
- 相关 lessons 条目（若有）。
- 工作分支：`autoloop/<run-id>`（所有代码改动落在此分支）。

## 执行者
Coding 型子代理。派遣提示必须包含：P3 技术方案全文、P2 PRD 中界面文案与流程要点、本模板"执行指令"全文、仓库编码规范要点（小程序用 `<view>/<text>` 与 `uni.*`、后端 async/await 与四层结构、管理后台 Element Plus + Tailwind）、相关 lessons 条目。

## 执行指令
1. **照方案实现**：文件清单逐个落实，数据契约逐字段落实；实现中发现方案有误或不完整时，先在报告中记录偏差与原因，再按合理方式实现——不要默默偏离。
2. **范围纪律**：只改方案涉及及直接依赖的文件；禁止顺手重构、禁止格式化无关代码、禁止删除方案未要求删除的内容。
3. **遵守仓库规范**：注释中文、命名与现有风格一致、新页面同步注册（如小程序 pages.json）、新路由/新模型按仓库规则注册。
4. 界面文案逐条使用 P2 的最终字符串，不得自行改写。
5. 本阶段结束时代码应可构建可运行（构建/测试的**正式验证在 P5 进行**，此处只需基本自查），自查中发现的失败如实记入报告"已知限制"。
6. 撰写实现报告：变更文件清单（与 P3 清单对照，逐文件标注 已按方案 / 有偏差 / 新增）、关键决策（实现中的取舍及理由）、已知限制（未解决的自查问题、技术债）。

## 必须产出物
- `artifacts/P4-implementation-report.md`（实现报告），固定章节：

| 章节 | 内容要求 |
|---|---|
| 变更文件清单 | 路径 / 改动摘要 / 与方案对照结果 |
| 关键决策 | 偏离方案的决策：背景 / 选择 / 理由 |
| 已知限制 | 未解决问题、技术债、风险点，如实列出 |

（注：代码变更本身也是本阶段产出，git diff 即证据。）

## 提交前自查清单

- [ ] `git status` 无未预期的未跟踪文件（构建产物、临时文件、调试脚本）。
- [ ] `git diff --stat` 的文件集合与报告变更清单完全一致（逐文件比对）。
- [ ] 新增 API 路由已注册到 router.py、新模型已在 models/__init__.py 导入、新页面已登记 pages.json（按仓库规则）。
- [ ] 无遗留调试代码（console.log / print 调试语句 / 注释掉的旧代码块）。
- [ ] 界面文案与 P2 逐字一致（抽查主要入口至少 5 处）。
- [ ] 代码可过基础构建（后端可 import 无语法错、前端可 build），失败项已列入已知限制。

## 迭代与改进约定

- 编排者触发本阶段 gate 时建议携带 `--include-diff`（把 `git diff HEAD` 与 `git status --short` 注入三个评审的提示词），使评审能直接引用代码证据，而不只凭实现报告文字判断。
- 本阶段 gate 失败后，用 `python3 .qoder/skills/autoloop/scripts/harness.py directives --run <run-id>` 获取改进指令，按指令修复代码并同步更新报告，在文件尾部追加「改进记录」一节（轮次 / 收到的指令 / 代码与报告的变更点）。
- 修复性改动同样受范围纪律约束：只改指令指向的问题，不顺手重构；新改动同步补入变更清单。
- 若指令指向的是方案层缺陷（P3 遗漏），在报告关键决策中新增偏差记录（背景=评审指令），再实现。
- 超过迭代上限（默认 5 轮）进入 blocked：停止修订，向用户呈报记分卡与未决指令，等待决策。

## 完成标准
- [ ] 变更文件清单完整覆盖实际 git diff 中的每个文件，无遗漏。
- [ ] 每个与方案的偏差均有决策记录（背景/选择/理由三要素齐全）。
- [ ] 已知限制如实列出（自查发现的问题不得隐瞒）。
- [ ] 实际改动文件集合 ⊆ P3 方案文件清单 ∪ 偏差声明文件集合（无未声明的超范围改动）。
- [ ] 界面文案与 P2 字符串一致（抽查主要入口）。
- [ ] 迭代轮次产生的改进记录完整可追溯（若经历过重评）。

## 评分要点（摘要）
- 最看重：方案符合度、报告与代码事实的一致性、范围纪律。
- 常见扣分：变更清单漏文件；偏差未声明却存在于 diff 中；已知限制空着但 P5 会暴露问题；文案与 PRD 不一致；报告写"完全按方案实现"但 diff 显示明显额外改动。
- veto 触发：存在未声明的超范围改动（动了方案与偏差声明之外的文件）；报告与代码事实不符（清单遗漏或谎报）；引入方案未授权的新依赖且未记录。
