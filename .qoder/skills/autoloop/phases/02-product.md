# P2 产品化设计（product）

## 目标
把 P1 需求卡转化为面向真实用户的产品设计文档（PRD）：用户在什么场景下如何使用这个功能、看到什么文案、怎样算成功。本阶段把"要做什么"翻译成"用户会遇到什么"，让下游技术方案有明确的体验靶子，也让 P8 阿尔法测试有可对照的操作路径。

## 输入
- `artifacts/P1-requirement-card.md`（上一阶段产物，全量读取）。
- 相关 lessons 条目（若有）。
- 仓库现有页面/交互模式（如需保持产品一致性，可参考现有端的界面结构，只读）。

## 执行者
Research 型子代理（产品视角的分析与写作，不做代码改动）。派遣提示必须包含：P1 需求卡全文、本模板"执行指令"全文、目标用户画像（EZLove：子女=小程序发送方、老人=大字体高对比阅读方、社区工作人员=管理后台操作方）、相关 lessons 条目。

## 执行指令
1. 用户故事按"角色-场景-价值"格式写：`作为<角色>，在<具体场景>下，我希望<操作>，以便<获得价值>`。每个故事对应 P1 范围内的一块功能面；老人端故事必须符合"零学习成本、牵挂而非监控"的产品策略。
2. 核心流程分步描述：从入口到完成的每一步（用户看到什么、点什么、系统反馈什么），**必须包含异常分支**（网络失败、数据为空、权限不足至少三类）。
3. 界面文案要**具体到字符串**：按钮文字、标题、提示语、空状态文案、确认弹窗文案，逐条写成最终上线的中文文案（EZLove 端文案从"关心"角度出发，禁止"监控/追踪/报警"类词汇；老人端字号与触控要求在设计说明中注明）。
4. 定义成功指标：可度量的指标（如使用率、完成率、响应时长阈值），写明取数口径。
5. 边界场景清单：极端输入、角色越权、空数据、重复提交、并发操作等，每条给出产品侧的预期表现。
6. 产物自包含，评审只读此文件即可理解产品设计全貌。

## 必须产出物
- `artifacts/P2-prd.md`（PRD），固定章节：

| 章节 | 内容要求 |
|---|---|
| 用户故事 | 角色-场景-价值格式，覆盖全部角色 |
| 核心流程 | 分步描述，含异常分支 |
| 界面文案要点 | 具体到最终字符串 |
| 指标 | 成功指标 + 取数口径 |
| 边界场景 | 场景 / 预期表现 |

## 质量对照示例

- 差的用户故事："支持菜单提醒"。→ 无角色、无场景、无价值。
- 好的用户故事："作为子女，在为父母绑定食堂订阅后，我希望每周日 18:00 收到本周菜单概览，以便提前知道父母哪几天会在食堂就餐"。→ 三要素齐全，可直接推导界面与推送设计。
- 差的文案："提示用户操作成功"。
- 好的文案："已发送给妈妈，她看到后会出现在已读列表里"。→ 具体、有温度、可直接入代码。

## 迭代与改进约定

- 本阶段 gate 失败后，用 `python3 .qoder/skills/autoloop/scripts/harness.py directives --run <run-id>` 获取改进指令，据此修订 PRD，并在文件尾部追加「改进记录」一节（轮次 / 收到的指令 / 修订内容），供评审核验改进轨迹。
- 修订只针对指令指向的问题，不重写未受影响的章节（保留已认可的成果，降低回归风险）。
- 修订时同步核对 P1 需求卡：若指令揭示的是需求层歧义，先在需求卡层面记录发现，再在 PRD 中以修订后的理解展开。
- 超过迭代上限（默认 5 轮）进入 blocked：停止修订，向用户呈报记分卡与未决指令，等待决策。
- PRD 是 P8 阿尔法测试的蓝本：写作时始终自查"这条内容将来能变成一条可执行的操作路径吗"。

## 完成标准
- [ ] 用户故事覆盖 P1 范围内全部角色，无"角色-场景-价值"要素缺失。
- [ ] 核心流程包含至少三类异常分支的处理描述。
- [ ] 界面文案全部为具体字符串（引用处逐条可抄进代码），无"显示相应提示"类抽象表述。
- [ ] 每个成功指标可度量且写明取数口径。
- [ ] 边界场景不少于 6 条，且每条有明确的预期表现。
- [ ] 与 P1 需求卡的范围一致，未私自扩围或漏项。
- [ ] 迭代轮次产生的改进记录完整可追溯（若经历过重评）。

## 评分要点（摘要）
- 最看重：文案具体度（能否直接抄进代码）、核心流程含异常分支的完整度。
- 常见扣分：用户故事写成功能列表无场景；文案停留在"提示用户"层面；异常分支缺失；指标无取数口径；边界场景少于 6 条。
- veto 触发：缺"核心流程"章节；文案含产品策略明令禁止的冷冰冰词汇（监控/追踪/报警）且未说明；范围与 P1 需求卡明显冲突。
