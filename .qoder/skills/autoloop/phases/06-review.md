# P6 代码评审（review）

## 目标
在放行发布之前，从三个互补维度对本次变更做独立代码评审并整合为一份报告：**完整性**（方案承诺的都实现了吗）、**正确性**（实现逻辑对不对）、**影响面**（会不会伤及无辜模块）。三个维度由三个相互独立的评审子代理并行执行，避免单一视角的盲区。

## 输入
- `artifacts/P3-tech-design.md`（方案承诺基准）、`artifacts/P4-implementation-report.md`（变更清单）、`artifacts/P5-verification-report.md`（已有证据）。
- 代码分支 `autoloop/<run-id>` 的完整 diff（评审的核心对象）。
- 相关 lessons 条目（若有）。

## 执行者
**3 个并行 CodeReview 型子代理**，各自只负责一个维度、互不通信：

| 子代理 | 维度 | 核心问题 |
|---|---|---|
| 评审-完整性 | 完整性 | 方案文件清单与数据契约逐项在 diff 中核销了吗？有无漏实现/偷工减料 |
| 评审-正确性 | 正确性 | 逻辑、边界、错误处理、并发、事务对吗？有无隐藏 bug |
| 评审-影响面 | 影响面 | 改动波及的调用方/数据消费方/共享组件会破坏吗？兼容性如何 |

每个评审子代理的提示必须包含：本模板"执行指令"全文、其负责维度的判定清单、P3/P4/P5 产物路径、diff 获取方式。**不得**向任一评审提供其他评审的任何中间结论。

由编排 Agent（或指定 1 个整合子代理）汇总三份结论写整合报告。

## 执行指令
1. 每个评审子代理实际读代码（不是只读报告）：完整性对照 P3 清单逐文件核销；正确性重点看新增/修改的核心逻辑分支、错误路径、空值处理、事务边界；影响面用调用方检索（谁引用了被改的函数/接口/表结构）核实。
2. **每个结论必须引用证据**：文件路径 + 行号（或函数名 + diff hunk），格式如 `backend/app/services/moment.py:L120-L134`。无引用的结论视为未发生。
3. 发现的问题分级：blocker（必须修复才能发布）/ major（应修复，可带条件放行）/ minor（建议项），每级附定位与修复建议。
4. 三份结论整合为一份报告：每个维度一节（结论 + 证据 + 问题清单），末尾给出整合判断——是否存在 blocker、放行前置条件。
5. 整合时矛盾处理：两个维度结论冲突（如完整性说实现了、正确性说逻辑错）不是删掉分歧，而是如实并列并标注待核实点。

## 必须产出物
- `artifacts/P6-review-report.md`（三维评审整合），固定章节：

| 章节 | 内容要求 |
|---|---|
| 完整性结论 | 逐项核销表 + 问题清单（分级） |
| 正确性结论 | 证据引用 + 问题清单（分级） |
| 影响面结论 | 兼容性分析 + 问题清单（分级） |
| 整合判断 | blocker 汇总 + 放行前置条件 |

## 派遣时序与独立性保障

1. 三个评审子代理**同提示、同时派遣**，各自独立会话；提示中不得含其他评审的任何结论或分数。
2. 评审产物先各自落盘为临时结论（由编排 Agent 收集），再由整合者读取汇总——整合前任何一方都看不到别人的结论。
3. 若某维度评审中途失败（超时/产物异常），单独重派该维度，不影响已完成的另两个维度。
4. 整合报告中的矛盾结论按"待核实点"如实并列，不得为了结论好看而抹平分歧。

## 迭代与改进约定

- 编排者触发本阶段 gate 时建议携带 `--include-diff`（把 `git diff HEAD` 与 `git status --short` 注入三个评审的提示词），使三评审能直接引用代码证据。
- 本阶段 gate 失败后，用 `python3 .qoder/skills/autoloop/scripts/harness.py directives --run <run-id>` 获取改进指令（可能指向代码修复或报告补充），据此重新执行受影响维度的评审（代码改了就必须重新读代码，不能只改报告），并在文件尾部追加「改进记录」一节。
- blocker/major 问题修复后，相关维度必须复评并给出"已修复/未修复"的复核结论，附新证据行号。
- 超过迭代上限（默认 5 轮）进入 blocked：停止修订，向用户呈报记分卡与未决指令，等待决策。

## 完成标准
- [ ] 三个维度各有独立结论，均含文件行号级证据引用。
- [ ] P3 文件清单在完整性维度逐项核销（实现/偏差/缺失三态）。
- [ ] 所有发现的问题已分级（blocker/major/minor）并附定位与建议。
- [ ] 整合判断明确回答"是否存在 blocker"及放行前置条件。
- [ ] 无"代码看起来没有问题"类的无证据结论。
- [ ] 迭代轮次产生的改进记录完整可追溯（若经历过重评）。

## 评分要点（摘要）
- 最看重：证据引用密度（行号级）、问题分级的准确度、三维度结论的独立性痕迹（视角差异可见）。
- 常见扣分：只复述 P4/P5 报告不读代码；结论无行号引用；把 major 问题轻描淡写成 minor；三维度结论雷同（疑似串评）。
- veto 触发：评审发现 blocker 级问题但整合报告未如实列入；任一维度结论被发现与代码事实不符（行号张冠李戴）；评审子代理之间被发现共享了结论。
