# P5 验证（verify）

## 目标
用**真实执行**的证据证明实现满足 P1 的每条验收标准。本阶段是流水线的诚实底线：所有构建、lint、测试、冒烟命令必须真实运行并原样粘贴输出，禁止编造、修编、想象任何输出。没跑的就写"未运行"，跑失败的就贴失败输出——失败本身是有效信息，编造才是原则性错误。

## 输入
- `artifacts/P1-requirement-card.md`（验收标准清单）与 `artifacts/P4-implementation-report.md`（变更文件清单）。
- `artifacts/P3-tech-design.md` 的测试策略章节。
- 代码分支 `autoloop/<run-id>` 的当前工作区。
- 相关 lessons 条目（若有）。

## 执行者
Verify 型子代理（以真实运行为唯一手段，不改业务代码；如遇环境问题可修测试环境/依赖配置并记录）。派遣提示必须包含：P1 验收标准全文、P4 变更清单、本模板"执行指令"全文、仓库命令速查（后端 uvicorn/alembic、前端 npm 脚本、docker-compose 启动 db/redis）、相关 lessons 条目。

## 执行指令
1. 逐条验收标准先写**验证方法**（命令或操作步骤），再真实执行，最后原样粘贴输出（含命令本身）。输出较长可截取关键段，但须保留判定所需的部分（错误信息、统计行、退出码）。
2. 至少包含四类证据（适用则做，不适用须写明为何不适用）：构建（build）、静态检查（lint）、测试（test，优先仓库已有测试命令）、冒烟（按核心流程手动/脚本走一遍）。
3. 环境准备如实记录：数据库/缓存如何启动（如 `docker-compose up -d db redis`）、迁移是否执行（`alembic upgrade head`）、种子数据是否使用。
4. **未覆盖项必须显式列出**：每条写明未覆盖的验收标准/场景 + 原因 + 风险评估。禁止用"基本覆盖"一笔带过。
5. 覆盖说明：给出"验收标准 → 证据"的对照表，让评审能逐条核销。
6. 发现的缺陷按严重度列出（critical/major/minor）并注明是否已在 P4 已知限制中声明——新发现的缺陷即使当场修复也要记录"发现→修复→复验"轨迹。

## 必须产出物
- `artifacts/P5-verification-report.md`（验证报告），固定章节：

| 章节 | 内容要求 |
|---|---|
| 命令与输出的真实证据 | 命令 + 原样输出，按类分组 |
| 覆盖说明 | 验收标准 → 证据对照表 |
| 未覆盖项与理由 | 逐条：未覆盖项 / 原因 / 风险 |

## 证据规范

- 每条证据三要素：**命令**（原样可复制粘贴重跑）、**关键输出**（含成功/失败标志行）、**结论**（对应哪条验收标准，判定依据是什么）。
- 失败输出处理：失败原样粘贴 + 原因分析 + 是否阻塞判定；当场能修的修复后重跑并保留两轮输出（失败→修复→通过是有效轨迹，不是污点）。
- 长输出截取规则：保留判定依据行（pytest 统计行、构建 success 标志、报错堆栈首尾），截取处标注"…（中间截取 N 行）"。
- 手动冒烟步骤同样按"操作 = 命令"记录（如 curl 全文、页面 URL + 操作序列 + 观察到的关键文本）。
- 证据时间性：全部证据须来自本轮验证会话（旧跑结果、P4 自查输出不算 P5 证据）。
- 环境可追溯：报告开头记录验证环境（分支、commit、数据库/服务启动方式、种子数据），评审可据此重建环境复现。

## 迭代与改进约定

- 编排者触发本阶段 gate 时建议携带 `--include-diff`（把 `git diff HEAD` 与 `git status --short` 注入三个评审的提示词），使评审能将验证证据与实际代码变更对照。
- 本阶段 gate 失败后，用 `python3 .qoder/skills/autoloop/scripts/harness.py directives --run <run-id>` 获取改进指令，重新执行受影响的验证项（不是只改报告文字），并在文件尾部追加「改进记录」一节（轮次 / 收到的指令 / 重跑的命令与输出）。
- 评审指令指向证据不足时，必须真实重跑补证据，禁止在无新运行的情况下改写结论。
- 验证中发现的代码缺陷由另派的 Coding 子代理修复（Verify 型不改业务代码），修复后由本阶段复验并补记。
- 超过迭代上限（默认 5 轮）进入 blocked：停止修订，向用户呈报记分卡与未决指令，等待决策。
- 本阶段产物是后续阶段的事实基础：P6 评审、P7 发布判断均引用验证结论，证据失真会让下游全部失真。

## 完成标准
- [ ] 每条 P1 验收标准在覆盖表中要么对应证据，要么列入未覆盖项（无第三种状态）。
- [ ] 所有粘贴输出与命令一致、可复现（评审可按命令重跑核对）。
- [ ] 构建/lint/测试/冒烟四类证据齐全（或写明不适用理由）。
- [ ] 未覆盖项每条有原因与风险评估，无空泛表述。
- [ ] 发现的缺陷全部分级列出，修复过的有复验证据。
- [ ] 迭代轮次产生的改进记录完整可追溯（若经历过重评）。

## 评分要点（摘要）
- 最看重：证据真实性（命令与输出可复现）、验收标准核销率（覆盖表逐条对得上）。
- 常见扣分：输出疑似截取但缺判定依据；覆盖表漏验收标准条目；"全部通过"却无输出粘贴；未覆盖项写"无"但明显有场景未测（如只测了正向流程）。
- veto 触发：**编造或篡改命令输出**（评审比对实际运行即可发现）；验收标准大部分无证据；把失败输出伪装成成功输出。
