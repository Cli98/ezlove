# P8 阿尔法测试（alpha-test）

## 目标
以真实用户视角对已发布准备就绪的功能做端到端实测：按 P2 用户故事设计操作路径，**真实执行**（Web/管理后台用浏览器子代理实际点出来；小程序/H5 用运行中的 dev 服务实走；CLI/API 用真实调用），收集反馈并形成缺陷分级与处置结论。阿尔法测试不是纸面推演——"计划测什么"必须配上"实际测到的记录"。

## 输入
- `artifacts/P2-prd.md`（用户故事与界面文案——测试路径的蓝本）与 `artifacts/P7-release-report.md`（冒烟基线）。
- 运行环境：本地起服务（`docker-compose up -d db redis` + uvicorn + 前端 dev，或 P7 构建产物），种子数据（`python seed_demo.py` 等）。
- 相关 lessons 条目（若有）。

## 执行者
Verify+Browser 型子代理（可实际操作浏览器/发起真实请求；发现问题只记录不修，修复另派 Coding 子代理后复测）。派遣提示必须包含：P2 用户故事与文案全文、P7 冒烟清单、本模板"执行指令"全文、环境启动命令、相关 lessons 条目。

## 执行指令
1. 依据 P2 每个用户故事设计**操作路径级**测试计划：入口→每步操作→预期界面反馈（预期必须引用 P2 的具体文案字符串）。
2. 真实执行：管理后台/网页用浏览器子代理逐路径操作并截图（或记录 DOM 关键文本）；小程序 H5 模式用浏览器实走；API 用 curl/httpx 真实调用。每条路径记录：实际操作序列、实际观察、与预期的一致性判定。
3. 每个核心流程的正向路径必测；P2 边界场景至少抽测 3 条（含 1 条异常分支）。
4. 反馈清单：执行中产生的一切体验问题（文案拗口、步骤多余、反馈缺失、加载无提示）逐条记录，无论是否算缺陷。
5. 缺陷分级与处置：critical（核心流程不可用/数据错误/安全问题）/ major（功能受损但有绕行）/ minor（体验瑕疵），每条给处置结论：已修复（附复测证据）/ 计划修复（排期依据）/ 延后（理由）/ 不修（理由）。
6. 明确声明**critical 缺陷清零**状态：任一 critical 未处置即在本产物中触发 veto 条件（见评分要点），不得进入下一阶段。

## 必须产出物
- `artifacts/P8-alpha-report.md`（阿尔法报告），固定章节：

| 章节 | 内容要求 |
|---|---|
| 测试计划 | 用户故事 → 操作路径 → 预期（引用 P2 文案） |
| 执行记录 | 每条路径：实际操作 / 实际观察 / 判定 |
| 反馈清单 | 逐条体验反馈（不限于缺陷） |
| 缺陷分级与处置 | 级别 / 定位 / 处置结论（含复测证据或理由） |

## 环境与数据准备

- 起服务：`docker-compose up -d db redis`，后端 `uvicorn app.main:app --reload`（端口 8001），管理后台 `npm run dev`（端口 5174），小程序 H5 `npm run dev:h5`（端口 5173）。
- 数据：使用种子脚本准备可测数据（如 `python seed_demo.py` / `python seed_elders.py`），测试账号与关键数据在报告中列明，避免评审复现时盲找。
- 环境差异：阿尔法在本地/预发环境执行，与生产存在差异（数据量、真实账号体系）之处在报告开头声明，避免结论外推过度。
- 留痕：浏览器子代理每条路径至少保留一项客观痕迹（截图路径、关键 DOM 文本、请求 URL + 响应码），供评审抽查。
- 视角约束：阿尔法测试模拟"第一次见到这个功能的真实用户"——不带实现知识的操作（不知道内部字段、不猜开发者的意图），发现"用户会困惑"的点比发现"代码错了"的点更重要。
- 隔离：测试产生的脏数据（新增记录、状态变更）在报告尾部注明清理方式或保留理由。

## 迭代与改进约定

- 本阶段 gate 失败后，用 `python3 .qoder/skills/autoloop/scripts/harness.py directives --run <run-id>` 获取改进指令，据此补充测试路径或修复缺陷处置结论，并在文件尾部追加「改进记录」一节（轮次 / 收到的指令 / 修订内容）。
- 修复缺陷另派 Coding 子代理，修复后由本阶段重测受影响路径并补记复测证据（与 P5 同群：发现→修复→复验闭环）。
- 若指令指向 P2 层面的问题（如文案不可用），在反馈清单中标注来源，供 P9 复盘归因，不在本阶段改 PRD。
- 超过迭代上限（默认 5 轮）进入 blocked：停止修订，向用户呈报记分卡与未决指令，等待决策。
- 本阶段是发布后、推广前的最后防线：从用户视角的结论优先级高于技术视角的"理论上可行"。

## 完成标准
- [ ] 测试计划覆盖 P2 全部用户故事，预期引用具体文案。
- [ ] 每条计划路径有对应真实执行记录（浏览器操作/请求+响应，非推演描述）。
- [ ] 核心流程正向路径 + ≥3 条边界场景有执行记录。
- [ ] 每个缺陷有分级与处置结论；标"已修复"的附复测证据。
- [ ] 报告明确声明 critical 缺陷处置状态（清零或列出未处置项）。
- [ ] 迭代轮次产生的改进记录完整可追溯（若经历过重评）。

## 评分要点（摘要）
- 最看重：执行真实性（操作记录/请求证据，而非"预期会正常"）、缺陷处置闭环（分级→处置→复验）。
- 常见扣分：测试计划未覆盖全部用户故事；执行记录写成功能描述而非操作序列；缺陷只列不处置；把 critical 降级为 major 蒙混；异常分支一条没测。
- veto 触发：**存在未处置的 critical 缺陷**（含声称修复但无复测证据）；执行记录被发现系编造（无真实运行痕迹）；核心正向路径未实际执行。
