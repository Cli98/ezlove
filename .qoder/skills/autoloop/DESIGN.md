# autoloop 整体设计文档

> 一句话需求 → 九阶段流水线 → 三模型评分门 → 自进化。本文档说明 autoloop 的设计动机、架构决策与安全边界，是理解"为什么这样设计"的权威参考。

## 1. 设计目标与哲学

autoloop 要解决的问题：用户只有一句话需求，但期望得到的是"做完到上线"的完整交付。传统做法要么是人工接力（需求→产品→开发→测试→发布，每一棒都损耗上下文），要么是单 Agent 一次性生成（质量不可控、无验证、无底线）。

autoloop 的四条设计哲学：

1. **一句话 → 全流程**：用户表达意图，流水线负责把意图展开为需求卡、PRD、技术方案、代码、证据、发布物——每一棒的上下文通过 artifacts 显式传递，不依赖对话记忆。
2. **质量门前置**：不在最后才发现问题。每个阶段的产物必须先过三模型评分门（≥95 分）才进入下一阶段，把返工成本压到最低的时点。
3. **持续优化而非一次成型**：失败不是异常而是常态。每次 gate 失败产出结构化改进指令，带着指令修订产物再评，循环收敛——模型写不好一次，但改得好的能力是真实存在的。
4. **自进化**：每轮 run 的经验沉淀进 lessons.md 注入下一轮，评分数据反哺 rubric 演进（人工批准制）。工具本身随着使用变准。

一句话概括：**用确定性的引擎管住不确定性的模型，用评分门逼出诚实的证据，用循环代替一次成型。**

                   │ 评分调用

        ┌────────────────────────┐

每阶段内部循环：`phase → 执行者产出 artifacts → gate → (通过？引擎自动推进下一阶段 : directives → 修复 → 重新 gate ...)`；blocked 后由用户批准 continue 恢复迭代。

## 3. 职责分离：语义归 Agent，确定性归脚本

autoloop 最重要的一条架构线：

| 职责 | 归属 | 理由 |
|---|---|---|
| 读模板、派遣子代理、理解指令、写产物 | 编排 Agent | 语义工作，模型擅长 |
| 状态流转（running/awaiting_ingest/blocked/done） | 引擎脚本 | 必须确定、可审计 |
| 评分聚合、阈值判定、迭代计数 | 引擎脚本 | 规则不能被模型"商量" |
| 改进指令的合并去重 | 引擎脚本 | 三评审指令的结构化汇总是机械操作 |
| 门禁结果判定（all ≥95 且无 veto） | 引擎脚本 | 放行与否是硬规则 |

为什么这样分：

1. **可审计**：每个 run 的全部历史（state.json、gates/score-history.jsonl）落盘为纯数据，事后可以复盘"为什么 P4 第二轮被拒"——纯 Agent 对话无法可靠审计。
2. **可断点续跑**：状态在脚本手里，会话中断后新会话按状态目录恢复即可，不依赖 Agent 的记忆连续性。
3. **防 Agent 幻觉改规则**：阈值 95、迭代上限 5、veto 语义都在脚本与配置里，Agent 再"觉得产物其实还行"也无法放行——规则的门钥匙不在它手里。
4. **Agent 专注语义**：把确定性工作卸载给脚本后，Agent 的注意力预算全部花在产物质量与子代理调度上。

代价是引入了 CLI 边界（Agent 必须一字不差地调用命令），换来的是机制刚性。SKILL.md 中的命令契约因此不可改写。

### 一次 gate 的完整数据流走查（local 模式）

以 P3 技术方案第一次 gate 为例，数据在三层间流动：

```
1. Agent: python3 .qoder/skills/autoloop/scripts/harness.py phase --run demo-001
   → 脚本读 state.json（当前阶段 P3）→ 输出模板路径 phases/03-tech-design.md
2. Agent: 读模板 → 派遣 Research 子代理（携带 P1/P2 产物 + 模板指令）
   → 子代理写 .autoloop/demo-001/artifacts/P3-tech-design.md
3. Agent: python3 .qoder/skills/autoloop/scripts/harness.py gate --run demo-001 --artifacts artifacts/P3-tech-design.md
   → 脚本校验 run 状态与产物存在（--artifacts 路径 resolve 后必须位于 run 目录内，越界报错退出 2）→ 未配 models.json → local 模式
   → 生成 gates/P3-iter1.prompts/A.md / B.md / C.md 三个评审提示词
   → 状态 running → awaiting_ingest
4. Agent: 并行派遣 3 个评审子代理（各自读自己的提示词 + 产物 + 代码）
   → 各自产出 verdict JSON（含分数/维度/证据/指令/veto）
5. Agent: python3 .qoder/skills/autoloop/scripts/scorer.py ingest --run demo-001 --evaluator A --file verdict-A.json
   → 脚本校验 schema → 写入 gates/ 对应 verdict 文件（ingest 全程持有文件锁，并行回填安全）
   → 同样回填 B、C；第三个 ingest 落地时自动判定：
      A=96, B=94, C=91 → strategy=all 不通过 → 生成改进指令汇总
      → 判定完成时立即向 gates/score-history.jsonl 追加一行
      （ts/run_id/phase/phase_name/iter/passed/scores/avg/min/directives_count；
      api 模式同样在判定完成时追加，P9 复盘执行期间该文件已存在）
   → 状态 awaiting_ingest → running（失败可重评；若通过则引擎
      自动推进 phase+1 并重置 iteration=1，无需手工干预）
6. Agent: python3 .qoder/skills/autoloop/scripts/harness.py directives --run demo-001
   → 输出去重后的指令清单（B 的契约字段缺失 + C 的回滚不可执行）
7. Agent: 派遣修复子代理 → 修订产物（尾部追加改进记录）
   → 回到步骤 3 重新 gate，直至三轮 ≥95 或迭代上限
```

注意步骤 5：判定发生在脚本内，Agent 无从干预——即使 Agent"觉得"94 分已经足够好。

## 4. 九阶段流水线详解

### P1 需求澄清（intake）
- **目的**：一句话 → 结构化需求卡。歧义全部转为"默认决策"（有理由的拍板），验收标准必须可验证。
- **产出**：`artifacts/P1-requirement-card.md`（背景/目标/范围/非目标/验收标准/开放问题与默认决策/风险）。
- **门禁要点**：验收标准可验证性是 A（产品专家）的核销重点；歧义留白直接 fail。

### P2 产品化设计（product）
- **目的**：需求卡 → 用户视角的 PRD。用户故事（角色-场景-价值）、到字符串级的界面文案、可度量指标、边界场景。
- **产出**：`artifacts/P2-prd.md`。
- **门禁要点**：文案具体度（能否直接抄进代码）与异常分支完整度；文案与产品策略冲突（冷冰冰词汇）触发 veto。

### P3 技术方案（tech-design）
- **目的**：PRD → 可照做的方案。文件清单到路径、契约到字段、回滚到命令。
- **产出**：`artifacts/P3-tech-design.md`。
- **门禁要点**：B（研发专家）核销文件清单与契约的具体性；无回滚方案 veto。

### P4 研发实现（implement）
- **目的**：照方案写代码 + 诚实记录。偏差必须声明，禁止超范围改动。
- **产出**：代码变更（git diff）+ `artifacts/P4-implementation-report.md`。
- **门禁要点**：报告与代码事实一致性（清单 vs diff）；未声明的超范围改动 veto。

### P5 验证（verify）
- **目的**：真实执行命令贴证据，逐条核销验收标准。
- **产出**：`artifacts/P5-verification-report.md`。
- **门禁要点**：证据真实性是 C（质量仲裁）的核心检查项；编造输出 veto。

### P6 代码评审（review）
- **目的**：三个独立子代理并行评审（完整性/正确性/影响面），整合为带行号证据的报告。
- **产出**：`artifacts/P6-review-report.md`。
- **门禁要点**：证据引用密度；发现 blocker 不报 veto。

### P7 发布（release）
- **目的**：版本/changelog/构建证据/部署步骤/冒烟/回滚，全部"准备就绪"。
- **产出**：`artifacts/P7-release-report.md`。
- **门禁要点**：回滚三要素（触发条件/步骤/数据处理）；**实际部署前必须用户确认（safety.auto_deploy=false）**，未经确认部署是 veto 级违规。

### P8 阿尔法测试（alpha-test）
- **目的**：真实用户视角实测（浏览器子代理实际操作），缺陷分级与处置闭环。
- **产出**：`artifacts/P8-alpha-report.md`。
- **门禁要点**：执行真实性（非纸面推演）；**未处置 critical 缺陷 veto**。

### P9 自进化复盘（evolve）
- **目的**：经验可泛化沉淀进 lessons.md、基于 score-history.jsonl 的数据分析、rubric 补丁提案。
- **产出**：`artifacts/P9-retro.md` + lessons.md 增量。
- **门禁要点**：数据分析必须引用具体数字；**擅自改 config/ 是 veto**（提案 ≠ 应用）。

### 阶段排序的设计理由

- **P1→P2→P3 严格串行**：需求合糊会污染 PRD，PRD 合糊会污染方案——上游一个字的歧义到下游就是一天的返工。宁可前期多迭代（文档改起来便宜），不要后期返工（代码改起来贵）。
- **P5（验证）在 P6（评审）之前**：先让证据说话，再让评审读证据。若顺序倒过来，评审会花大量精力质疑"有没有跑过"而非"跑的结果对不对"；P5 的证据让 P6 的三维评审有事实锚点。
- **P6 是唯一的多代理阶段**：三维并行评审（完整性/正确性/影响面）对应三类典型生产事故：漏实现（完整性）、逻辑错（正确性）、改坏了别的（影响面）。单评审单视角必然漏掉其中之一。
- **P7 在 P8 之前**：发布准备（版本/构建/回滚）先就绪，阿尔法测试才能在"可发布状态"上测——测的才是将来真实存在的东西。
- **P9 永远最后**：复盘需要全部阶段的完整数据（九份产物 + score-history），提前复盘等于盲人摸象。

## 5. 三模型评分门机制设计

### 5.1 为什么是 3 个评审

- **独立性**：单模型自评有系统性偏差（生成者给自己打分偏高）。三个独立评审互不可见分数，串分与"看着别人给高分我也给高"的锚定效应被结构性切断。
- **视角多样性**：A 产品专家盯"这是不是用户要的"，B 研发专家盯"这在工程上站不站得住"，C 质量仲裁盯"证据链是否诚实完整"。三个视角的短板互补，一个视角的盲区大概率被另一个视角覆盖。
- **抗操纵**：想通过门禁必须同时说服三个不同立场，比说服一个评审难得多——这是刻意的。

### 5.2 为什么 strategy=all 且 95 分

- **宁严勿滥**：本工具的信任模型是"流水线输出的东西可以直接用"。任何一票 <95 都不放行，保证通过门禁的产物没有已知短板。
- **95 分的语义**：95-100 被定义为"生产级、证据充分、无可挑剔"。这不是 100 分制里的"优秀学生"（85 就算优秀），而是"拿着放大镜找茬也只能吹毛求疵"的标准——生产环境里，可挑剔意味着事故。
- **代价的自觉**：严门槛必然带来更多迭代轮次。我们用迭代上限（5 轮）+ blocked 人工介入兜底死循环，用改进指令的结构化传递保证每轮迭代是真改进而不是重摇骰子。

### 5.3 反分数通胀设计（机制核心）

LLM 评审的天然缺陷是分数通胀（随口给 90+）。autoloop 用七层设计对抗：

1. **证据强制**：每个分数必须引用证据（产物章节、代码行号、命令输出）。无证据支撑的评分被 cap 到 90——低于门槛，等于自动失败。这把"打分"变成"举证"。
2. **persona 差异化**：C（质量仲裁）的人设是三者中最严的（对证据链、诚实度、边界情况的怀疑者），提示词明确要求"宁可错杀不可放过"。
3. **评审独立性**：三评审互不可见分数与评语（并行派遣、独立会话、verdict 分别落盘），防止锚定与从众。
4. **veto 一票否决**：原则性问题（编造证据、超范围改动、无回滚、未处置 critical 缺陷、未经确认部署）不看总分直接 fail。分数可以讨价还价，原则不可以。
5. **迭代上限防死循环**：默认 5 轮，超限 blocked 转人工。既防"改到天荒地老"，也防评审和执行者陷入"你改一点我扣一点"的猫鼠游戏。
6. **零指令兜底**：gate 失败（veto 或 evidence 为空）必产生兜底指令——veto 生成 critical 级指令、evidence 空生成 major 级指令，确保修复子代理永远有明确工作清单，失败不会"无指令可用"而空转。
7. **avg 策略证据硬门**：任一评审 evidence 为空 → 直接不通过（不再经过 cap 与 min_per_model 的分数协商）——证据硬门优先于分数协商，堵住"无证据但高分"的组合漏洞。

### 5.4 api 模式 vs local 模式（诚实说明）

- **api 模式**：`config/models.json` 配置三个**真实异构模型**（例如 DeepSeek / Claude / Qwen 分任 A/B/C）。这是机制的完全体——异构模型的偏好差异天然抑制共谋，评分独立性有物理基础。api key 走环境变量 `AUTOLOOP_EVAL_A_KEY` / `AUTOLOOP_EVAL_B_KEY` / `AUTOLOOP_EVAL_C_KEY`，不落盘。
  - **基础设施错误不烧迭代**：网络/HTTP/超时/密钥错误属于配置故障而非产物质量失败——gate 以退出码 2 结束，不计入迭代、状态不变，并提示检查配置（网络异常自动重试一次，重试携带失败原因）。设计动机：区分"产物不行"与"环境不行"，环境抖动不应白白烧掉迭代预算；仅"模型有返回但解析失败"才按 0 分计入判定（质量信号）。
  - **`--include-diff` 的动机**：api 模式评审默认只能看到产物文本，代码类阶段（P4 实现 / P5 验证 / P6 评审）的评审需要代码证据可达。携带该 flag 会把 `git diff HEAD` 与 `git status --short`（合计截断 6000 字符）注入三个评审提示词，使评审能直接引用代码证据而非仅凭报告文字。
- **local 模式**：未配置 API 时，脚本生成 3 个评审提示词文件，由编排 Agent 派遣**同一模型的 3 个 persona 子代理**并行评审，verdict 经 `python3 .qoder/skills/autoloop/scripts/scorer.py ingest --run <id> --evaluator A --file <verdict.json>` 逐个回填（ingest 全程持有文件锁，三个评审并行提交安全）。离线可用、零成本，但独立性弱于异构模型（同模型的系统性偏差无法互相抵消，防串分完全依赖派遣纪律）。
- **选型建议**：生产/重要 run 用 api 模式；快速试验、无外网、成本敏感场景用 local 模式。local 模式的结论建议在心里打个小折扣——它的 95 分比 api 模式的 95 分证据效力弱。

### 5.5 verdict 数据流

```
gate --run <id> --artifacts <产物>
  ├─ api:  脚本直调三模型 → verdict JSON × 3 → 聚合判定
  └─ local: 生成 3 个评审提示词 → 状态 awaiting_ingest
            → 3 个评审子代理独立产出 verdict JSON
            → python3 .qoder/skills/autoloop/scripts/scorer.py ingest --run <id> --evaluator A/B/C 逐个回填
            → 第三个 ingest 落地时自动判定 → 状态回 running/blocked
```

verdict JSON 的完整 schema 见 reference.md。

### 5.6 评分维度与权重设计

每个阶段的 rubric（细则见 config/rubrics.json，语义说明见 reference.md）由 4-5 个维度加权构成，权重分配原则：

- **本阶段不可妥协的维度权重最高**（如 P5 的证据真实性 30 分、P3 的数据与接口 15 分）——权重即优先级声明。
- **单一维度权重 10-30**：任一维度塌方到 0 分而其余维度满分时，加权总分 = 100 - 权重 ≤ 90（最小权重 10），必低于 95 门槛——单项塌方不可能被其他项平均掉，每个维度都是独立的质量闸门。
- **维度与阶段特性绑定**：文档阶段（P1-P3）量"具体度"（到路径/到字段/到字符串），执行阶段（P4-P8）量"真实性"（证据可复现、报告与事实一致）。
- **三评审共享同一套维度但视角不同**：A 从用户价值看维度、B 从工程可行性看维度、C 从证据链完整性看维度——同一维度三种问法，分歧即信号。

这套设计让"卷面分"不可能漂亮：任一维度塌方 → 该维得分低 → 总分被拉下 95；无证据 → cap 90；原则问题 → veto。三条路全部堵死。

## 6. 持续优化循环

gate 失败不是终点而是数据：

1. **指令结构化**：每个评审在 verdict 的 `issues[].directive` 字段给出具体改进指令（"P3 文件清单缺 router.py 的注册改动，补上"而非"方案不够细"）。
2. **指令合并去重**：`python3 .qoder/skills/autoloop/scripts/harness.py directives --run <id>` 汇总三评审指令并去重——多评审指向同一问题时只出现一条（去重后的指令列表是修复子代理的工作清单）。
3. **修复定向**：修复子代理只改指令指向的问题，不重写产物（保护已通过的部分，降低回归风险）。产物尾部的「改进记录」让评审看见改进轨迹。
4. **重评收敛**：重新 gate。理想轨迹是分数逐轮上升直至 ≥95；若 5 轮不收敛，说明问题超出当前执行者能力或需求本身有矛盾。
5. **blocked 人工介入**：blocked 时向用户呈报记分卡（各评审历轮分数+指令）与三个选项：继续加迭代 / 调整产物方向 / 终止 run。人工介入点选在"机器已经证明自己搞不定"的时点，既不浪费人的注意力，也不让机器空转烧 token。

### 失败模式与对策

机制设计时预判的失效场景与防护：

| 失败模式 | 症状 | 对策（已内置） |
|---|---|---|
| 评审分数通胀 | 三评审集体给 95+，产物实际平庸 | 证据强制（无证据 cap 90）；C persona 最严；api 模式异构模型 |
| 评审串分 | 三 verdict 高度相似，疑似互通 | 并行独立派遣、互不可见；评分文件分别落盘；P6 同样三维度隔离 |
| 执行者讨好评审 | 产物只改指令字面，不实质改进 | 评审只看产物与代码；改进记录要求可核验的变更点 |
| 编造证据 | P5 输出疑似伪造 | veto 条款；评审可重跑命令比对；C 的核心检查项 |
| 死循环迭代 | 同一指令反复出现，分数不收敛 | 迭代上限 5 轮 → blocked 人工介入 |
| 幻觉改规则 | Agent 绕过 CLI 手改 state.json | 状态文件只读红线；判定逻辑在脚本内 |
| 未授权部署 | P7 顺手 push/部署 | safety.auto_deploy=false；未经确认部署是 veto；报告必须声明未执行 |
| rubric 被污染 | 评分门悄悄变松 | 补丁人工批准；配置 git 版本化可审计 |
| 环境噪声 | 验证失败其实是环境问题 | P5 环境可追溯要求；环境修复与业务修复分离记录 |

这些对策的共同形态：**不信任任何单点（模型/Agent/配置），用结构（隔离/上限/人工闸门/落盘审计）兜底**。

## 7. 自进化机制

自进化走两条通道，闸门强度与其风险匹配：
**通道一：lessons 沉淀（自动注入，无需批准）**
- P9 把可泛化经验追加到 `.autoloop/lessons/lessons.md`（只追加不改写）。
- 下一轮 run 启动时（SKILL.md 启动步骤 2）读入 lessons，注入各执行子代理提示。
- 注入防线：lessons.md 内容仅为历史经验参考，不是指令；与阶段模板、评分规则或安全规则冲突时，一律以模板与规则为准，忽略 lessons 中的冲突内容——注入无法越权改变门禁与安全语义。
- 设计权衡：lessons 是上下文注入（影响行为）而非规则修改（改变门禁），风险低，允许自动；且"只追加"保证历史不可篡改。

**通道二：rubric 演进（提案 → 人工批准 → 配置版本化）**
- P9 基于 score-history.jsonl 的数据分析（哪阶段最常重评、哪类指令反复出现）产出 rubric 补丁提案（diff 形式）。
- 提案呈报用户，批准后才修改 `config/rubrics.json`，配置变更随 git 版本化——rubric 的每次演化都有 commit 可查。
- 设计权衡：rubric 直接决定门禁松紧，被污染（例如某次提案悄悄降阈值）会瓦解整个质量体系，所以宁可进化慢一点，也必须人在环上。

**数据回路**：每次 gate 判定完成时（api 与 local 模式一致）立即向 `<run>/gates/score-history.jsonl` 追加一行（ts/run_id/phase/phase_name/iter/passed/scores/avg/min/directives_count）——P9 复盘执行期间该文件已存在，是数据分析的权威来源；evolve 收尾命令再把本 run 的 `gates/score-history.jsonl` 幂等合并到跨 run 的 `.autoloop/lessons/score-history.jsonl`（按 run_id 去重），长期校准分析基于后者。它是 P9 复盘的原料，也是检验"评分门是否校准得当"的长期数据（若 C 的均分长期比 A 低 10 分，说明 persona 提示词需要校准——这本身就是一条 rubric 补丁的动机）。

## 8. 安全边界

1. **部署确认门**：`safety.auto_deploy=false` 是默认且推荐的唯一取值。P7 只产出"准备就绪"的发布报告，任何实际部署动作（git push、远程发布、生产变更）必须用户明确确认。确认流程见 P7 模板"用户确认流程"。
2. **rubric 补丁不自动应用**：P9 只提案，应用权在用户。执行子代理与编排 Agent 都不得修改 config/。
3. **独立分支**：`git checkout -b autoloop/<run-id>`，所有变更隔离在 run 分支——失败可整体丢弃，成功可整体评审合并。
4. **状态目录 gitignore，技能文件入库**：`.autoloop/`（run 状态、评分、lessons）是本地运行时数据，不进版本库（避免评分噪声污染代码 diff 与 PR）；技能文件本身已通过 .gitignore 白名单入库（`config/models.json` 与 `__pycache__` 仍忽略）——模板与 rubric 的演进有 commit 可查，rubric 演进可审计的承诺由此成立。
5. **blocked 必须人工决策**：自动循环的上限本身就是安全机制——机器的固执不能替代人的判断。
6. **状态文件只读**：Agent 不得手工编辑 state.json / gates/ / reports/，一切变更走 CLI——这是"确定性归脚本"的具体落地。

## 9. 与 Qoder 编排的关系

autoloop 运行在 Qoder 的编排模型上：

- **编排 Agent = Qoder Leader**：主会话执行 SKILL.md 的主循环，负责子代理调度与用户交互。
- **执行者/评审/修复子代理**：按阶段模板"执行者"一节的角色派遣（Research/Coding/Verify/CodeReview/Browser 型）。子代理数量随阶段动态变化（P6 需 3 个并行评审 + 1 个整合）。
- **任务看板映射**：九个阶段天然映射为看板上的九个任务；每阶段的 gate 迭代轮次对应任务的进行中状态；blocked 对应"需要用户输入"状态。编排 Agent 可据此更新 TodoWrite/TaskList。
- **渐进披露**：SKILL.md 只放主循环，阶段细节在 phases/、评分细节在 reference.md——按需读取，控制上下文预算。

## 10. 拒绝的替代方案

设计过程中权衡过但最终放弃的方案，及放弃理由（防止未来"优化"时重踩）：

| 被拒方案 | 曾看似的优势 | 拒绝理由 |
|---|---|---|
| 单评审模型（一个 LLM 一次评完） | 成本降为 1/3，延迟低 | 自评偏差无法抑制；分数通胀不可控；门禁公信力塌方 |
| 85 分门槛 + 多数决（两票过即放行） | 迭代轮次少，流水线快 | 与"生产级可用"目标冲突；85 分意味着存在已知缺陷的产物直接进下游 |
| 评审可见彼此分数后协商终分 | 能消除分歧、结论更一致 | 一致性恰恰是问题：分歧是有价值的信号，协商会退化成锚定 |
| 让 Agent 自己维护状态（不用脚本） | 减少 CLI 摩擦 | 状态可被幻觉篡改；不可审计；断点续跑不可靠 |
| 全自动部署（auto_deploy=true） | 真正的无人值守 | 部署是不可逆动作的代表，出错代价高于少按一次确认键的成本 |
| rubric 补丁自动应用 | 进化更快 | 评分门是安全机制，机制自我修改等于让被监管者改监管规则 |
| 失败后整体重写产物（不限定修复范围） | 每轮都是"全新视角" | 丢掉已通过部分引发回归；评审每次从零看起成本高；改进不可追溯 |

共同取舍模式：**速度与成本让位于可信与可控**——autoloop 的存在意义不是快，是"敢用"。

## 11. 扩展点

1. **自定义阶段**：在 `config/harness.json` 的 phases 数组中增删阶段（如插入"安全审计"阶段），并在 phases/ 放对应模板——引擎按配置驱动，模板路径由 phase 命令输出。
2. **策略扩展**：strategy 除 `all` 外可扩展（如 `majority` 两票通过）——但默认坚持 all，放宽须用户显式配置。
3. **CI 集成**：harness.py 的 CLI 天然可脚本化——CI 中跑 `python3 .qoder/skills/autoloop/scripts/harness.py gate --run <id> --mode api` 作为 MR 质量门，把 autoloop 从 Agent 编排工具降维用作纯评分服务。
4. **多 run 并行**：状态目录按 run-id 隔离，`python3 .qoder/skills/autoloop/scripts/harness.py list` 可枚举——多个需求各自成 run 互不干扰（注意 git 分支与工作区的独占性，建议串行或在独立 worktree 中并行）。
5. **rubric 市场**：lessons.md 与 rubrics.json 均为纯文本配置，团队间可共享校准好的 rubric 包。
