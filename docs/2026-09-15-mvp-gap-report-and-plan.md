## 0. 执行摘要（一分钟版）

1. **功能骨架完成度远高于"差很多"**：后端 19 个路由域约 80-85% 可用，管理后台约 75%，小程序 UI 约 85%。真正缺的不是功能，而是**安全修复、发布链路、部署加固和测试基线**。
2. **交接文档基本可信但已过时**：15 项后端声明 14 项属实；但文档描述的 Git 状态（分支 fix/admin-baseurl-fallback、脏工作区）与当前工作区（main @ 943ff35、完全干净）不符，且有两处声明已被后续代码修复（admin token 刷新、多社区切换）。**以代码为准，不以文档为准。**
3. **核实发现一个交接文档未提及的严重回归**：`3509210` 提交将 4 个列表接口改为分页响应后，4 个前端 store 未同步解包 `.items`，导致**小程序首页/历史/提醒列表和管理后台老人/事件两张核心表格当前无法正确渲染**。这是全项目性价比最高的止血点（约半天工作量）。
4. **最快 MVP = 管理后台先行 + 小程序体验版跟进**：管理后台无微信审核依赖，修完安全和可用性问题即可在现网试点；小程序真机使用受 HTTPS 域名/ICP 备案/微信资质等**日历时间约束**，必须第 1 天就启动申请，工程与外部审批并行。
5. **总工程量约 25-30 人日，2 名开发 3 周可交付试点版 MVP**（详见第 5 节）。

## 2. 产品专家视角：差距判断与 MVP 范围裁剪

### 2.1 产品价值的真实差距排序

EZLove 的产品灵魂是两条闭环 + 一条铁律：

- **家庭闭环**：子女发牵挂 → 老人查看 → 已读即在线 → 未读提醒子女。
- **社区闭环**：多源信号 → 异常队列 → 网格员电话/走访 → 人工确认 → 状态回写。
- **铁律**：老人零学习成本 + 牵挂而非监控的文案。

对照代码，三条的现状：

1. **家庭闭环后端已通，但前端入口断了**——老人到达路径 5 步且含登录+选角色+邀请码绑定，老人实际用不起来；订阅消息模板空缺意味着"未读提醒"送不到子女微信。**这条闭环当前只在演示环境成立。**
2. **社区闭环基本成立**——工作台/楼栋下钻/人工确认/风险评分/时间线都在，管理后台无微信审核依赖，**是当前最快能产生真实价值的入口**。缺口是列表回归损坏、超时面板死功能、新增要手填 UUID。
3. **铁律部分失守**——小程序禁用词干净、适老化达标；但后台 13 处"告警"文案与"零学习成本"的老人路径需重点投入。

### 2.2 MVP 范围定义（建议）

**目标用户**：溪东社区 15 名工作人员 + 首批 10-20 个家庭（约 20-40 位 A/B 类老人）试点。

**MVP 必做（三条核心闭环 + 上线底线）**：

| 闭环 | MVP 内容 |
|---|---|
| 家庭闭环 | 发送/查看/回应/未读提醒（含订阅消息真实送达）；老人路径压缩为"点卡片即看" |
| 社区闭环 | 工作台异常队列（含真实超时判断与总数）、老人列表分页+搜索、老人详情、人工确认、楼栋下钻 |
| 食堂信号 | 文本录入 + AI/规则解析 + A/B 缺席事件（Excel 上传保留现有实现，不作为验收项） |
| 上线底线 | 四类越权修复、隐私协议页、每日备份+恢复演练、发布配置注入（AppID/域名/模板 ID） |

**MVP 明确砍掉（不宣传、不投入）**：

| 砍掉项 | 理由 |
|---|---|
| AI 媒体（照片修复/视频生成/动画化） | 后端模型未接入恒 503，且前端有降级提示；接入是 XL 级独立项目 |
| 邻里帮志愿者运营闭环 | 依赖 C 类老人微信绑定，试点期无运营人力；页面保留不推广 |
| 海报生成增强、AI 助手新工具 | 现有实现够用（AI 助手有关键词兜底） |
| 两套积分体系合并 | 无试点场景，纯技术债，V2 处理 |
| 食堂就餐规范化表（批次+明细） | JSONB 在 40 人试点规模完全够用，2000+ 全量导入前再做 |
| RBAC 完整权限模型 | 试点期 15 人一个社区，role_label 标签够用；但**越权校验（横向）不能省** |
| unionid、多端账号打通 | 单小程序 MVP 用不到 |
| 大屏模式打磨、DESIGN.md 全面对齐 | 演示资产已够，试点验收不看这个 |

**两处产品原则的务实妥协（需明确决策）**：

1. **老人直达链路**：完整方案（分享卡片+静默授权+深链保持）约 L-XL。MVP 快路径建议：分享 moment 详情页卡片 + 启动静默 `wx.login`（后端已支持自动建号）+ 保留深链；首次绑定仍用邀请码但由子女/工作人员协助完成（试点家庭少，可人工兜底）。完整匿名 token 方案放 V1.1。
2. **老人档案与微信账号绑定**：正式 `elder_wechat_bindings` 表（迁移+核验流程+审计）约 L。MVP 试点期沿用 `community_elders.elder_id` 由工作人员代绑（20-40 人可控），**全量真实导入前必须完成正式绑定模型**（列入 V1.1 硬门槛）。

### 2.3 商业/运营视角的最快路径判断

- **管理后台先行**：现网已有 HTTP 入口和演示数据，修完安全+回归+可用性即可让 15 名工作人员真实使用，**第 1-2 周即可产生价值并收集真实反馈**。
- **小程序体验版跟进**：真机使用强制要求 HTTPS 合法域名 → 域名+ICP 备案+证书是**日历关键路径（约 1-2 周+，不可压缩）**，微信类目/隐私审核再加数天。结论：**第 1 天启动申请，第 3 周体验版真机验收**。
- 试点规模刻意小（20-40 老人），目的是验证"已读即在线"信号质量与工作人员工作流，而非覆盖率。

**明确推迟到 V1.1/V2（记录不遗忘）**：elder_wechat_bindings 正式绑定模型（V1.1 硬门槛）、RBAC、调度分布式锁（单进程约束写入部署文档）、timestamptz 全表迁移、食堂规范化表、限流改造、unionid、AI 媒体接入、积分合并、完整测试体系与 CI/CD。

### 3.2 关键技术决策

1. **时间口径**：MVP 采用"naive 本地时间 + 本地自然日"最小方案，禁止 aware/naive 再混写；在 `deps.py` 或公共 utils 提供唯一 `now()`/`today_start()` 函数收口。
2. **单进程约束**：MVP 期间 uvicorn 保持单 worker 单副本（调度器无锁），写进部署 README；扩容前置条件 = 调度锁改造。
3. **配置回灌优先于新功能**：线上 nginx/compose 与仓库不一致意味着"从仓库重建"会直接失败，第 1 周必须完成核实与回灌。
4. **测试策略**：不追求覆盖率，只建三类用例——越权矩阵（每修复项必须有红灯用例）、核心闭环冒烟、迁移可执行（新库 `alembic upgrade head` 冒烟）。
